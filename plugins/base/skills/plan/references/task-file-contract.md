# Task File Format

Each task file is a complete specification for a single atomic task in the plan. The executing agent reads this file and works through it step by step.

## Schema

Resources follow the contract defined in `resource-type-contract.md`.

```yaml
id: 01-<kebab-case-title>          # matches the file name without .yml
status: pending                    # pending | in_progress | completed | blocked
dependsOn: []                      # task IDs that must complete first
title: "<short imperative title>"
commit: "<semantic commit message>"

description: |
  <What this task delivers end-to-end. Explain WHAT, not HOW.
  Never mention specific files, commands, or implementation details.
  2-4 sentences.>

decisions:
  - <task-specific technical decision distilled from the PRD>

constraints:
  - <task-specific constraint distilled from the PRD>

steps:
  - description: "<what to do>"
    status: pending            # pending | in_progress | completed
    resources:
      - type: skill | command | file | prompt
        value: "<identifier>"
        purpose: "<why this resource is relevant>"
    progress: []               # filled during execution
  - description: "run full test suite, type check, lint, build"
    status: pending
    resources:
      - type: command
        value: "bun test && bun run typecheck && bun run lint && bun run build"
        purpose: "final verification"
    progress: []

learnings: []                      # filled after task completion
```

## Field rules

### Status tracking

Two levels of status enable precise resumability:

- **Task level**: `status` — overall task progress
- **Step level**: `steps[].status` — each atomic action

All statuses start as `pending` when generated by `/plan`. They are updated to `in_progress` and `completed` as work progresses during execution.

### Steps

Steps are granular, vertical-slice actions. Each step describes **what** to do, not **how**.

The last step should always be a "final verification" that runs the full test suite, type check, lint, and build.

**Resources** follow the same contract as `plan.config.yml` — see `resource-type-contract.md` for the full schema and type definitions.

**Progress** is an array of strings filled in after executing each step. It captures what was actually done, files touched, decisions made, and results.

### Learnings

An array of strings populated after completing all steps. Captures reusable insights discovered during implementation — extracted patterns, gotchas, or conventions worth sharing. Significant learnings that are general to the project should be persisted to the project's `AGENTS.md`.

## Generation

Generate task files one at a time, in order. For each task:

1. Read the plan context from `plan.yml` (overview, decisions, constraints, edge cases).
2. Read `.agents/plan.config.yml` and incorporate its resources into steps — match resources to the step's phase (setup, testing, implementation, verification, refactoring).
3. Define steps — granular, vertical-slice actions that together deliver the task end-to-end.
4. Write the task YAML to `.agents/plans/<plan-name>/<task-id>.yml` using the Write tool.
5. Briefly confirm what was generated (task title, number of steps) before moving to the next. Do not ask for approval — the task breakdown was already approved.

### Guidelines

- All task file content must be in English regardless of the user's language.
- `description` explains WHAT to deliver, never HOW — no specific files, commands, or implementation details.
- `progress` arrays start empty — they are filled during execution.
- `learnings` starts as an empty array.
- Step descriptions should be specific enough to be actionable but general enough to allow implementation flexibility.

### Skill discovery

Global skills for testing, verification, and refactoring are already defined in `.agents/plan.config.yml`. During task file generation, you may encounter **domain-specific** capabilities that need a skill (e.g., form patterns, component architecture, API design) not yet covered in the plan config.

**If the skill is already in plan.config.yml** — use it directly, do not ask the user.

**If a domain-specific skill is needed but not in plan.config.yml** — pause and resolve it before continuing:

1. Check your system prompt — available skills are listed there, regardless of whether they're project-local, global, or from external plugins.
2. Ask the user with AskUserQuestion which of their available skills handles this capability. List the skills you can see as options.
3. Add the confirmed skill to the `implementation` section of `.agents/plan.config.yml` following `resource-type-contract.md`.

**If no available skill covers the capability:**

1. Invoke `/find-skills` to search for a matching community skill.
2. If the user installs a new skill, add it to the `implementation` section of `.agents/plan.config.yml`.
3. If the user declines, add a `type: prompt` resource to the `implementation` section instead — an inline instruction describing what to do for that capability.

This knowledge accumulates incrementally — once a skill is added to plan.config.yml, it applies to all subsequent task files in this plan and in future plans. Do not ask again for capabilities already resolved.

## Example: pending task (as generated by `/plan`)

```yaml
id: 03-notification-badge
status: pending
dependsOn: [01-create-read-notifications]
title: notification badge with live polling
commit: "feat(notifications): add unread badge to nav with 30s polling"

description: |
  Add a badge to the main navigation showing unread notification count.
  Polls the unread-count endpoint every 30 seconds. Clicking the badge
  navigates to the notifications page.

decisions:
  - polling every 30s, not websockets
  - badge shows "99+" for counts over 99
  - badge hidden when count is 0

constraints:
  - must not cause layout shift when badge appears/disappears
  - concurrent tabs should sync via storage event

steps:
  - description: "write unit test: GET /api/notifications/unread-count returns { count: number } for authenticated user"
    status: pending
    resources:
      - type: file
        value: src/tests/api/notifications.test.ts

    status: pending
    resources: []
    progress: []
  - description: "implement GET /api/notifications/unread-count"
    status: pending
    resources:
      - type: file
        value: src/api/notifications.ts
        purpose: "existing notifications API"
    progress: []
  - description: "run tests — should pass"
    status: pending
    resources:
      - type: command
        value: bun test
        purpose: "run test suite"
    progress: []
  - description: "write unit test: badge visible when count > 0"
    status: pending
    resources:
      - type: file
        value: src/tests/components/nav.test.tsx
        purpose: "existing nav component tests"
    progress: []
  - description: "write unit test: badge hidden when count is 0"
    status: pending
    resources: []
    progress: []
  - description: "write unit test: badge shows 99+ for counts over 99"
    status: pending
    resources: []
    progress: []
  - description: "implement badge component in nav with 30s polling"

      - type: file
        value: src/components/nav.tsx

    progress: []
  - description: "run tests — should pass"

    resources:
      - type: command
        value: bun test
        purpose: "run test suite"
    progress: []

    status: pending
    resources: []
    progress: []
```
